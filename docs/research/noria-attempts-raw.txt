Building a core banking system is a massive undertaking, and choosing Rust with Noria is a highly performant approach. Noria’s dynamic dataflow architecture excels at maintaining real-time materialized views, which is perfect for computing live account balances, rolling cashflows, and ledger aggregations without expensive recalculations on every read.
To fulfill your requirement—keeping the core business logic strictly on the server while leveraging WebAssembly (WASM) for a lightning-fast browser GUI—we will set up an architecture where:
The Rust Backend runs an async HTTP/WebSocket server (using axum) that holds the Noria database connection and executes all financial logic.
The WASM Frontend (using a framework like Yew or Leptos) acts purely as a thin client, rendering the UI and sending requests to the backend API.
The Noria DB processes the transaction streams and maintains materialized views of the accounting states.
Here is the foundational server setup to get you started.

2. The Main Server Logic (src/main.rs)
This main.rs file bootstraps the application, connects to the Noria instance (which uses ZooKeeper for discovery), mounts the core banking modules, and serves the WASM frontend.
Rust
use axum::{
    routing::{get, post},
    Router, Extension,
};
use noria::ControllerHandle;
use std::sync::Arc;
use tower_http::services::ServeDir;
use tracing_subscriber;
// Declare the business logic modules.
// You will create these files next (e.g., src/accounting/mod.rs)
mod accounting;
mod cashflows;
mod payments;
mod transactions;
/// Shared application state injected into all HTTP handlers
pub struct AppState {
    /// The Noria controller handle used to create mutators (writes) and getters (reads)
    pub db: ControllerHandle,
}
#[tokio::main]
async fn main() -> Result<(), anyhow::Error> {
    // 1. Initialize logging
    tracing_subscriber::fmt::init();
    tracing::info!("Starting Core Banking Engine...");
    // 2. Connect to Noria
    // Noria relies on ZooKeeper to manage its cluster state.
    // By default, ZK runs on 127.0.0.1:2181 locally.
    let zookeeper_addr = "127.0.0.1:2181";
    tracing::info!("Connecting to Noria cluster via ZooKeeper at {}", zookeeper_addr);
    let db = ControllerHandle::from_zk(zookeeper_addr).await?;
    let shared_state = Arc::new(AppState { db });
    // 3. Build the API Router
    let api_routes = Router::new()
        // We will define the sub-routes inside each module
        .nest("/accounting", accounting::router())
        .nest("/payments", payments::router())
        .nest("/cashflows", cashflows::router())
        .nest("/transactions", transactions::router());
    // 4. Build the Main Application Router
    let app = Router::new()
        // Mount the API routes under /api/v1
        .nest("/api/v1", api_routes)
        // Inject the shared Noria connection pool into the request lifecycle
        .layer(Extension(shared_state))
        // Serve the WASM frontend.
        // When you compile your Rust WASM frontend, output it to a "dist" folder.
        .fallback_service(ServeDir::new("dist"));
    // 5. Start the Server
    let addr = std::net::SocketAddr::from(([127, 0, 0, 1], 8080));
    tracing::info!("Server listening on http://{}", addr);
    axum::Server::bind(&addr)
        .serve(app.into_make_service())
        .await?;
    Ok(())
}

How this Architecture Meets Your Requirements
Absolute Server Authority: Because the axum API handles all Noria mutators, the WASM client cannot bypass business rules (like ensuring double-entry accounting balances out). The WASM frontend only sends intents (e.g., POST /api/v1/transactions/post).
Noria's Dataflow for Banking: In banking, calculating end-of-day balances or cashflow aggregations across millions of rows is expensive. With Noria, you will write a SQL materialized view like SELECT account_id, SUM(amount) FROM ledger GROUP BY account_id. Noria pre-computes this and updates it incrementally as new transactions arrive. When your WASM GUI requests an account balance, the Rust server reads it in O(1) time.
WASM Integration: You will create a completely separate Cargo workspace (or sub-crate) for the frontend, compiling it using wasm-pack build --target web --out-dir ../dist. The ServeDir::new("dist") in main.rs will serve this instantly to the browser.

The errors you're encountering indicate that noria depends on an unstable Rust feature called impl_trait_in_assoc_type. While this feature was available in nightly builds in the past, changes in the Rust compiler's nightly channel over the years have broken compatibility with noria's specific syntax for this feature (such as the unconstrained opaque type and mismatched types errors).
The Noria project hasn't been actively maintained to keep up with the latest Rust nightly breaking changes.
To fix this and successfully compile Noria, you need to downgrade your nightly toolchain to an older, specific version where noria is known to compile successfully.
Here is how to resolve it:
Step 1: Install a Compatible Nightly Toolchain
The Noria repository historically recommended specific nightly versions (like nightly-2020-06-04 or similar from the 2019-2020 era when the project was most active).
Run this command in your RustRover terminal (inside the /Users/checolino/RustroverProjects/GBS directory) to install and set an older, stable-for-Noria nightly version:
Bash
# This installs a nightly version from when Noria was actively developed
rustup toolchain install nightly-2021-01-01
# Set this specific version for your GBS project
rustup override set nightly-2021-01-01
(Note: If 2021-01-01 still gives you issues, try nightly-2020-10-01 or nightly-2019-11-01, as Noria's exact last-compatible date requires some trial and error depending on the 0.9 release you are pulling).
Step 2: Clean the Cargo Cache
Because Cargo has already attempted to compile these crates with your current (too-new) nightly compiler, you need to wipe the build cache so it starts fresh with the older compiler.
Bash
cargo clean
Step 3: Run the Project
Now, try running the project again:
Bash
cargo run
An Alternative: Using type_alias_impl_trait
If you still see errors about impl_trait_in_assoc_type after downgrading, it's because older versions of Rust called this feature type_alias_impl_trait before it was renamed.
If Noria fails to compile even on older nightlies, you may have to fork the Noria crate and change the feature flag at the top of their src/lib.rs from #![feature(impl_trait_in_assoc_type)] to #![feature(type_alias_impl_trait)], though downgrading your toolchain usually bypasses this need.

How do I set up the SQL schemas for accounts and transactions, and create the Noria materialized views via SQLx?
Because Noria acts as a MySQL proxy, you create your tables and materialized views using standard SQL commands. Noria intercepts CREATE TABLE to set up its base tables and intercepts CREATE VIEW to construct its high-performance, incrementally updated dataflow graphs.
In core banking, you should never store an account balance as a static, updateable number. Instead, you use an immutable ledger (append-only debits and credits) and calculate the balance on the fly. Noria is perfectly designed for this: it will continuously pre-compute the SUM() of the ledger in the background so reading a balance remains instantaneous, even with millions of transactions.
Here is how to set up the schemas, views, and handlers using sqlx.
1.Define the Database Schema:
We will use a standard double-entry ledger format. Money is represented in cents (as BIGINT) to prevent floating-point rounding errors.
Create a new file at /Users/checolino/RustroverProjects/GBS/backend/src/schema.rs to hold our initialization queries:
Rust
// backend/src/schema.rs
use sqlx::MySqlPool;
pub async fn initialize_db(pool: &MySqlPool) -> Result<(), sqlx::Error> {
    // 1. Create the base Accounts table
    sqlx::query(
        "CREATE TABLE IF NOT EXISTS accounts (
            id BIGINT,
            owner_name VARCHAR(255),
            PRIMARY KEY(id)
        );"
    ).execute(pool).await?;
    // 2. Create the append-only Ledger table
    // Positive amounts are credits, negative are debits.
    sqlx::query(
        "CREATE TABLE IF NOT EXISTS ledger (
            id BIGINT,
            account_id BIGINT,
            amount BIGINT,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
            PRIMARY KEY(id)
        );"
    ).execute(pool).await?;
    // 3. Create the Noria Materialized View
    // Noria intercepts this and builds a real-time dataflow graph.
    // NOTE: Noria might throw an error if the view already exists,
    // so in a production app you'd check for its existence first.
    let _ = sqlx::query(
        "CREATE VIEW account_balances AS
         SELECT account_id, SUM(amount) AS balance
         FROM ledger
         GROUP BY account_id;"
    ).execute(pool).await;
    Ok(())
}
Tip: We use the standard sqlx::query("...") function rather than the sqlx::query!("...") macro. The macro requires a live database connection at compile-time, which can act unpredictably with Noria's custom SQL dialect.
2.Create the Accounting Endpoints:

// backend/src/accounting.rs
use axum::{Extension, Json, Router, routing::{get, post}, extract::Path};
use serde::{Deserialize, Serialize};
use sqlx::{MySqlPool, Row};
use std::sync::Arc;
use crate::AppState;
pub fn router() -> Router {
    Router::new()
        .route("/transfer", post(process_transfer))
        .route("/balance/:account_id", get(get_balance))
}
#[derive(Deserialize)]
pub struct TransferPayload {
    pub from_account: i64,
    pub to_account: i64,
    pub amount_cents: i64,
}
#[derive(Serialize)]
pub struct BalanceResponse {
    pub account_id: i64,
    pub balance_cents: i64,
}
// Write to the base tables
async fn process_transfer(
    Extension(state): Extension<Arc<AppState>>,
    Json(payload): Json<TransferPayload>,
) -> &'static str {
    // In a real banking app, you would wrap this in a SQL transaction
    // and generate secure UUIDs/Snowflake IDs for the ledger rows.
    // 1. Debit the sender
    let _ = sqlx::query("INSERT INTO ledger (id, account_id, amount) VALUES (?, ?, ?)")
        .bind(rand::random::<i64>().abs()) // Dummy ID generator for demo
        .bind(payload.from_account)
        .bind(-payload.amount_cents)
        .execute(&state.db)
        .await;
    // 2. Credit the receiver
    let _ = sqlx::query("INSERT INTO ledger (id, account_id, amount) VALUES (?, ?, ?)")
        .bind(rand::random::<i64>().abs()) // Dummy ID generator for demo
        .bind(payload.to_account)
        .bind(payload.amount_cents)
        .execute(&state.db)
        .await;
    // Noria automatically sees these inserts and updates the `account_balances` view in milliseconds.
    "Transfer Processed"
}
// Read from the Noria Materialized View
async fn get_balance(
    Path(account_id): Path<i64>,
    Extension(state): Extension<Arc<AppState>>,
) -> Json<BalanceResponse> {
    // This query hits the Noria materialized view, meaning it doesn't actually
    // scan the ledger table. It just returns the pre-computed sum instantly.
    let row_result = sqlx::query("SELECT balance FROM account_balances WHERE account_id = ?")
        .bind(account_id)
        .fetch_one(&state.db)
        .await;
    let balance_cents = match row_result {
        Ok(row) => row.try_get("balance").unwrap_or(0),
        Err(_) => 0, // Account not found or zero balance
    };
    Json(BalanceResponse {
        account_id,
        balance_cents,
    })
}

    let id_2 = rand::random::<i64>().abs();
    // 1. Debit the sender
    let _ = sqlx::query("INSERT INTO ledger (id, account_id, amount) VALUES (?, ?, ?)")
        .bind(id_1)
        .bind(payload.from_account)
        .bind(-payload.amount_cents)
        .execute(&state.db)
        .await;
    // 2. Credit the receiver
    let _ = sqlx::query("INSERT INTO ledger (id, account_id, amount) VALUES (?, ?, ?)")
        .bind(id_2)
        .bind(payload.to_account)
        .bind(payload.amount_cents)
        .execute(&state.db)
        .await;
    "Transfer Processed"
}
// Read from the Noria Materialized View
async fn get_balance(
    Path(account_id): Path<i64>,
    Extension(state): Extension<Arc<AppState>>,
) -> Json<BalanceResponse> {
    let row_result = sqlx::query("SELECT balance FROM account_balances WHERE account_id = ?")
        .bind(account_id)
        .fetch_one(&state.db)
        .await;
    let balance_cents = match row_result {
        Ok(row) => row.try_get("balance").unwrap_or(0),
        Err(_) => 0,
    };
    Json(BalanceResponse {
        account_id,
        balance_cents,
    })
}

use axum::{Router, routing::get, Extension};
use sqlx::mysql::MySqlPoolOptions;
use std::sync::Arc;
pub struct AppState {
    pub db: sqlx::MySqlPool,
}
#[tokio::main]
async fn main() -> Result<(), anyhow::Error> {
    tracing_subscriber::fmt::init();
    tracing::info!("Starting GBS Backend on Stable Rust...");
    // Connect to Noria via its MySQL proxy port
    let database_url = "mysql://root:rootpassword@127.0.0.1:3306/gbs_db";
    let pool = MySqlPoolOptions::new()
        .max_connections(5)
        .connect(database_url)
        .await?;
    // 1. Create the base table for the immutable ledger
    sqlx::query(
        "CREATE TABLE IF NOT EXISTS ledger (
            id BIGINT PRIMARY KEY,
            account_id BIGINT,
            amount BIGINT
        );"
    ).execute(&pool).await?;
    // 2. Create the Noria Materialized View for instant balance lookups
    // Noria intercepts this and maintains it in real-time.
    let _ = sqlx::query(
        "CREATE VIEW account_balances AS
         SELECT account_id, SUM(amount) AS balance
         FROM ledger
         GROUP BY account_id;"
    ).execute(&pool).await;
    let shared_state = Arc::new(AppState { db: pool });
    // 3. Build the Router
    let app = Router::new()
        .route("/api/health", get(|| async { "GBS API is live" }))
        .layer(Extension(shared_state));
    // 4. Start the Server
    let addr = std::net::SocketAddr::from(([127, 0, 0, 1], 8080));
    tracing::info!("Server listening on http://{}", addr);
    axum::Server::bind(&addr).serve(app.into_make_service()).await?;
    Ok(())
}

use yew::prelude::*;
use reqwest::Client;
#[function_component(App)]
fn app() -> Html {
    // State to hold the response from our Axum backend
    let api_response = use_state(|| String::from("Waiting for backend..."));
    let ping_backend = {
        let api_response = api_response.clone();
        Callback::from(move |_| {
            let api_response = api_response.clone();
            // Spawn an async task in the browser's event loop
            wasm_bindgen_futures::spawn_local(async move {
                let client = Client::new();
                // We use a relative path; Trunk will proxy this to Axum
                let res = client.get("/api/health").send().await;
                match res {
                    Ok(response) => {
                        let text = response.text().await.unwrap_or_default();
                        api_response.set(text);
                    }
                    Err(e) => {
                        api_response.set(format!("Error connecting to backend: {}", e));
                    }
                }
            });
        })
    };

            <p>{ "WASM GUI running successfully." }</p>
            <button onclick={ping_backend} style="padding: 10px; cursor: pointer;">
                { "Ping Axum Backend" }
            </button>
            <div style="margin-top: 20px; padding: 10px; background: #eee;">
                <strong>{ "Backend Status: " }</strong> { (*api_response).clone() }
            </div>
        </main>
    }
}
fn main() {

    yew::Renderer::<App>::new().render();

use axum::{Router, routing::get, Extension};
use sqlx::mysql::MySqlPoolOptions;
use std::sync::Arc;
pub struct AppState {
    pub db: sqlx::MySqlPool,
}
#[tokio::main]
async fn main() -> Result<(), anyhow::Error> {
    tracing_subscriber::fmt::init();
    tracing::info!("Starting Core Banking Backend...");
    // Connect directly to Noria's MySQL proxy port
    let database_url = "mysql://127.0.0.1:3306";

        .connect(database_url)
        .await?;
    // 1. Create the immutable ledger

        "CREATE TABLE IF NOT EXISTS ledger (
            id BIGINT,
            account_id BIGINT,
            amount BIGINT,
            PRIMARY KEY(id)
        );"
    ).execute(&pool).await?;
    // 2. Create the Noria Materialized View for rolling balances
    let _ = sqlx::query(
        "CREATE VIEW account_balances AS
         SELECT account_id, SUM(amount) AS balance
         FROM ledger
         GROUP BY account_id;"
    ).execute(&pool).await;
    let shared_state = Arc::new(AppState { db: pool });
    let app = Router::new()

        .layer(Extension(shared_state));

    tracing::info!("Server listening on http://{}", addr);
    axum::Server::bind(&addr).serve(app.into_make_service()).await?;

use axum::{Router, routing::get, Extension};
use sqlx::postgres::PgPoolOptions;
use std::sync::Arc;
pub struct AppState {
    pub db: sqlx::PgPool,
}
#[tokio::main]
async fn main() -> Result<(), anyhow::Error> {
    tracing_subscriber::fmt::init();
    tracing::info!("Starting GBS Core Banking Backend...");
    // Connect to Materialize using the PostgreSQL wire protocol
    let database_url = "postgres://materialize@127.0.0.1:6875/materialize";
    let pool = PgPoolOptions::new()
        .max_connections(5)
        .connect(database_url)
        .await?;
    // 1. Create the immutable double-entry ledger (NO primary key constraint)
    sqlx::query(
        "CREATE TABLE IF NOT EXISTS ledger (
            id BIGINT,
            account_id BIGINT,
            amount BIGINT
        );"
    ).execute(&pool).await?;
    // 2. Create the Materialized View
    // Materialize incrementally updates this in milliseconds whenever a ledger row is inserted.
    let _ = sqlx::query(
        "CREATE MATERIALIZED VIEW IF NOT EXISTS account_balances AS
         SELECT account_id, SUM(amount) AS balance
         FROM ledger
         GROUP BY account_id;"
    ).execute(&pool).await;
    let shared_state = Arc::new(AppState { db: pool });
    let app = Router::new()
        .route("/api/health", get(|| async { "GBS API is live and connected to Materialize!" }))
        .layer(Extension(shared_state));
    let addr = std::net::SocketAddr::from(([127, 0, 0, 1], 8080));
    tracing::info!("Server listening on http://{}", addr);
    axum::Server::bind(&addr).serve(app.into_make_service()).await?;
    Ok(())
}

use axum::{Router, routing::get, Extension};
use sqlx::postgres::PgPoolOptions;
use std::sync::Arc;
pub struct AppState {
    pub db: sqlx::PgPool,
}
#[tokio::main]
async fn main() -> Result<(), anyhow::Error> {
    tracing_subscriber::fmt::init();
    tracing::info!("Starting GBS Core Banking Backend...");
    let database_url = "postgres://materialize@127.0.0.1:6875/materialize";
    let pool = PgPoolOptions::new()
        .max_connections(5)
        .connect(database_url)
        .await?;
    // Create the immutable ledger (no primary key needed for Materialize)
    sqlx::query(
        "CREATE TABLE IF NOT EXISTS ledger (
            id BIGINT,
            account_id BIGINT,
            amount BIGINT
        );"
    ).execute(&pool).await?;
    // Create the Materialized View for instant balances
    let _ = sqlx::query(
        "CREATE MATERIALIZED VIEW IF NOT EXISTS account_balances AS
         SELECT account_id, SUM(amount) AS balance
         FROM ledger
         GROUP BY account_id;"
    ).execute(&pool).await;
    let shared_state = Arc::new(AppState { db: pool });
    let app = Router::new()
        .route("/api/health", get(|| async { "GBS API is live and connected to Materialize!" }))
        .layer(Extension(shared_state));
    let addr = std::net::SocketAddr::from(([127, 0, 0, 1], 8080));
    tracing::info!("Server listening on http://{}", addr);
    axum::Server::bind(&addr).serve(app.into_make_service()).await?;
    Ok(())
}

use axum::{Router, routing::get, Extension};
use sqlx::postgres::PgPoolOptions;
use std::sync::Arc;
pub struct AppState {
    pub db: sqlx::PgPool,
}
#[tokio::main]
async fn main() -> Result<(), anyhow::Error> {
    tracing_subscriber::fmt::init();
    tracing::info!("Starting GBS Core Banking Backend...");
    // 1. Connect as the standard 'materialize' user
    let database_url = "postgres://materialize@127.0.0.1:6875/materialize";
    let pool = PgPoolOptions::new()
        .max_connections(5)
        .connect(database_url)
        .await?;
    // 2. Create a dedicated schema that our user owns
    sqlx::query("CREATE SCHEMA IF NOT EXISTS gbs;")
        .execute(&pool).await?;
    // 3. Create the immutable ledger inside our new 'gbs' schema
    sqlx::query(
        "CREATE TABLE IF NOT EXISTS gbs.ledger (
            id BIGINT,
            account_id BIGINT,
            amount BIGINT
        );"

    // 4. Create the Materialized View inside the 'gbs' schema
    // We explicitly assign it to the 'default' compute cluster required by v0.68.0

        "CREATE MATERIALIZED VIEW IF NOT EXISTS gbs.account_balances IN CLUSTER default AS
         SELECT account_id, SUM(amount) AS balance
         FROM gbs.ledger
         GROUP BY account_id;"

How do I add the POST /api/transfer endpoint in Axum to write double-entry transactions to Materialize?
To implement a robust double-entry transfer, we must enforce strict audit constraints: every transfer must insert two corresponding rows (a debit and a credit) atomically. If one fails, the entire transaction must roll back.
In Materialize (which uses Postgres drivers), we achieve this by wrapping the inserts in a SQL TRANSACTION.

async fn process_transfer(
    Extension(state): Extension<Arc<AppState>>,
    Json(payload): Json<TransferRequest>,
) -> Result<String, (StatusCode, String)> {
    // We explicitly use a database transaction to ensure atomicity
    let mut tx = state.db.begin().await.map_err(|e| {
        (StatusCode::INTERNAL_SERVER_ERROR, format!("Failed to start transaction: {}", e))
    })?;
    // Generate a unique transaction ID (for a real system, use UUID or a sequence)
    let transaction_id = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)
        .unwrap()
        .as_millis() as i64;
    // 1. Debit the sender (negative amount)
    sqlx::query(
        "INSERT INTO public.ledger (id, account_id, amount) VALUES ($1, $2, $3)"
    )
    .bind(transaction_id)
    .bind(payload.from_account)
    .bind(-payload.amount)
    .execute(&mut *tx)
    .await
    .map_err(|e| (StatusCode::INTERNAL_SERVER_ERROR, format!("Debit failed: {}", e)))?;
    // 2. Credit the receiver (positive amount)
    // We increment the transaction ID slightly so the primary key remains unique
    sqlx::query(
        "INSERT INTO public.ledger (id, account_id, amount) VALUES ($1, $2, $3)"
    )
    .bind(transaction_id + 1)
    .bind(payload.to_account)
    .bind(payload.amount)
    .execute(&mut *tx)
    .await
    .map_err(|e| (StatusCode::INTERNAL_SERVER_ERROR, format!("Credit failed: {}", e)))?;
    // Commit both rows to the ledger
    tx.commit().await.map_err(|e| {
        (StatusCode::INTERNAL_SERVER_ERROR, format!("Failed to commit transaction: {}", e))
    })?;
    Ok(format!("Successfully transferred {} from account {} to account {}", payload.amount, payload.from_account, payload.to_account))
}
